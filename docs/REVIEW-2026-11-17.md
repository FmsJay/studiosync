# Review of 2026-11-17 (0.58.91): what was found, fixed, and left

Six reviewers read 0.58.91 by area: mirror sync, the event and file pipeline, Live sync and transport, the panel and UI scripts, setup and
services and security, prints and automatic edits. Every finding was checked against the code before it counted. 0.58.92 fixes the ones
below; docs/TEST-PLAN.md says which tests cover them.

## Fixed in 0.58.92
Serious:
- mirror's "gone here" loop took the section's own keys ("fxk <oid>", "master fxen held") for deleted objects and overwrote them every pass:
  knob checks failed after the first minute (modulated chains re-sent and reprinted at every open) and the band's master FX switch went
  back on for everyone from a machine running SonoBus or NINJAM on the master.
- Live sync let in any computer asking over the studio's Tailscale: a guest as a full member (no end, no project list), and someone removed
  straight back. Now never someone taken out, and nobody while a guest invitation is open; a failed add is tried again after a minute.
- A guest's project list failed open while Syncthing was slow or the guest's mark couldn't be checked yet. It now fails closed, keeps the last
  list across a restart, and a guest let in as a member has theirs cleared.
- The status heartbeat stopped during a take: after 45 s the others read you as gone and took full control.
- A side-by-side stop counted one glitched playhead reading as two (reached() asked twice a pass). (0.58.91 regression)
- together_take outlived its take, so a redo of your own could be stopped by the leader's next cue.
- "Restore whole project to here" on a version older than every History entry deleted everything, for everyone. Disabled there now.
- A track's FX held off for a print stayed off once that part was deleted or got a second real take.
- Two tempo/marker changes at once left two computers with different maps for good (our own map didn't count). The newest wins now,
  ours included, ordered as takes and tracks are (a map made here comes after the newest seen here, whatever the clocks say: 0.58.93).
- Prepare session promised a backup on an unsaved project and made none: it goes to StudioSync's own folder now.

Smaller:
- A file unreadable for 10 minutes went on no list: it's on Health's skipped list now, and Try again reads it again.
- Old prints were never removed: the history trim archives the prints only the changes it archives named (in any room of the song), and
  the Drive copy doesn't bring them back.
- Ending a stuck background render could kill whatever had its process id by then: only a REAPER is ended.
- Enter in the chooser's New folder box also opened the song. Draw's Clear mine asks first. "By takes" colours count real takes.

The ones that were "plausible, not yet checked":
- A band deletion of a track took your unsent items on it: they go to "<track> (yours, not sent)" first.
- A refused edit deleted your item when the band's version waited for its recording: it stays now.
- A MIDI print wasn't redone after a slip edit or a play-rate change (its hash has both when they aren't the usual).
- Drive copied Syncthing's half-arrived files; and "James" read "James-Laptop"'s files as his own on Drive (both wrote them).
- Syncthing calls froze REAPER when Syncthing hung: after one call runs into its limit, the rest answer nothing for a minute.
- History trim ran as REAPER closed (it reads every change of the room): only in 20 quiet minutes now.
- Quoting: a --home with a space on Windows lost its quotes (PowerShell's outer quotes); O'Brien broke the Mac/Linux scripts; a studio name
  went into a folder label unquoted. The Syncthing API key is in a curl config file in the user's temp folder, off every command line.

Also fixed from the reviewers' smaller notes: lanes_back read a side room's track event from the wrong folder and remembered reset lane plays;
older_form missed a third empty take in a row; a % in a room name broke plain_event; takes_to_lanes and the tempo undo blocks could stay open
after an error; trust's cached verdicts were keyed by time only; band.read could bring back a file removed on purpose (band.remove);
a rename rewrote band.json for everyone and could wipe names.json on a half-synced read; deleting this computer's copy asks again who
holds it once you say yes, and Drive doesn't count without js_ReaScriptAPI (nothing tells how long a file has been there); a quick cue caught
mid-write is read again; the metronome is put back if Live sync stops mid count-in; an update's reload keeps the session's change count;
the together clock keeps its best reading (a late tick no longer moves starts); an error in the panel's bars closes their child; a failed
action registration is tried again and said; removing a stand-in says if it failed; bringing a room back asks; Take control's wait stops if
its tab goes; Final mix only picks up a file its render made.

## Checked and not a problem
- "Two songs open at once share state": every tab runs its own Live sync, in its own Lua state; module tables aren't shared.

## Left, with why
- The updater fetching from a third-party repo unpinned: James, 0.58.92: fine as it is.
- Permission rules are checked by the sender's StudioSync. A receiver holds a refused change for a minute (for claims and handovers still on
  their way), then lets it land so the projects don't split. Since 0.58.92 that minute is from when it arrived here, not the sender's clock.
  A changed copy of StudioSync (or one marking its changes "made alone") could still get through: the band trusts each other's copies.
  Time zones never mattered: every shared time is UTC, and both age functions read both sides as UTC.
- While a part plays its print, the track's FX are off for the whole track, so a new part on it with no print yet plays without them until
  it's printed (seconds, on the owner's computer). Per item isn't possible: FX are per track.
- A print rendered in front (no background renderer) while a sampler still loads can come out silent and isn't retried until the notes change.
- Ctrl+Z on "takes became lanes" is caught only while the redo is still that one (a change landing first clears it).
- The quick cue check walks the events folder's names every 0.25 s while someone else is here (seen files are skipped; no reads).
- The earlier review's Access items (Tailscale members reach every port, no web-interface password, members can bring computers, unindexed
  files believed) stay as docs/REVIEW-2026-11-16.md has them; Tailscale is parked.

## Second look, 0.58.93
Four reviewers read everything 0.58.92 changed, plus its tests. Fixed:
- Tempo maps by the sender's clock alone ("timeline at"): a computer whose clock ran ahead made every later map look older. Now ordered with
  newest_key "timeline", like takes and tracks.
- The Syncthing back-off never fired on Windows: REAPER answers "259" (still running) when the limit runs out, and curl "28" for its own -m
  (measured). Now it does; and a change (add, delete, set) always goes, only questions wait. A bandmate's computer not added during one is
  tried again in two minutes (it was never tried again).
- Guest lists: the people in charge read the list as written (access.read: a check still waiting showed nothing ticked, and ticking one song cut
  the guest to that one); a guest invited again for every project, or let in by Tailscale as a band computer, has an old list cleared; a list
  not checked yet shows the last checked one, which is kept only when checked; a studio from before owners counts its lists; each verdict is
  kept for that writing (it was a blocking call every 5 s in every tab).
- Live sync: the heartbeat covers Live set playing and the undo wait too; a record start REAPER's Record Warning cancelled doesn't count as a
  take started together; a reload's hand-over can't reach another Live sync.
- Tailscale auto-admit reads marks and invitations as written, checked or not (in the window before a check someone just taken out could come
  back).
- Track-delete keep: the kept item is yours (no band id, nothing waiting); the FX-hold recheck only on tracks holding FX (every item asked,
  track by track); a put-back waiting for a recording says so; trim reads what's still named from the folder as it is, older {media} form too.
- Drive without js_ReaScriptAPI says why it can't count; the curl config file is this user's only (chmod 600); renames use band.remove.
- The panel's bars error is said once and the rest of the panel goes on; Final mix names to the second.
- Tests: the timeline and empty-takes checks call the real code; test_review93 (Live sync's decisions, Drive, local copy, guest lists, the
  back-off, the key file) keeps its temp files in memory; print_archive and prepare_backup remove what they make; removal checks auto-admit.
Left: a print's hash now has the item's start offset and play rate, so split or slipped MIDI parts print once more after updating (on each
owner's computer). Taking the old hash as current would keep a slip edit's stale print. Two people saying yes to deleting their copies within
Syncthing's delivery time can still both go (the Recycle Bin has them). The style stack inside the panel's bars isn't unwound on an error.
